Prove my repo builds on a fresh machine

Demonstration

A fresh-environment build clones one exact commit on your PC, resets a bare lab machine to its clean baseline, runs your entrypoints silently inside it and writes a receipt. Read the full detail in Run a fresh-environment build.

  1. Check which hypervisor will be used

    VMware Workstation is used when vmrun answers; otherwise VirtualBox.

  2. Fetch and verify the evaluation media

    The official Windows 11 Enterprise evaluation ISO is downloaded from Microsoft and checked. See Media and verification.

  3. Create a bare lab machine

    A machine for an agent stays bare on purpose, so the build has to fetch every dependency itself. Expect 25 to 50 minutes the first time.

  4. Run the fresh-environment build

    The exit code is 0 only when every entrypoint passed.

          Host a runner for a private repo

          Demonstration

          A lab machine can host a self-hosted GitHub Actions runner for a private repository. The registration token travels on standard input and is cleared as soon as the guest has used it. Full detail: Register a self-hosted runner.

          Repository visibility
          mvl refuses this registration. It reads the repository's visibility through gh and refuses anything that is not private, because a self-hosted runner on a public repository would run strangers' pull requests.

          1. Create the lab machine

          2. Register the runner with a token on standard input

            Inside the guest the latest actions/runner release is downloaded, its SHA-256 checked and registered as a service.

          3. Use it in a workflow

            Labels: .

          4. Remove it when you are done

            A machine hosting a runner is never reset by mvl build or mvl up, so the runner is never orphaned. mvl rm removes every registration before deleting the machine.
